# Retro: vòng đầu tiên chạy thử quy trình (todo-cli, 0.1.0)

## Bối cảnh
Đây là lần chạy đầu tiên toàn bộ 9 giai đoạn của quy trình (docs/quy-trinh-phat-trien-phan-mem.md) trên một project mẫu thật (todo-cli), từ `/requirements` đến `/release`. Người dùng đánh giá chung: quy trình rõ ràng, dễ theo, không thấy bước nào thừa.

## Cái gì hiệu quả
- `/requirements` dùng câu hỏi trắc nghiệm (AskUserQuestion) để chốt phạm vi/lưu trữ nhanh hơn nhiều so với hỏi mở — nên tiếp tục dùng cách này khi có thể.
- ADR 2 phương án ở `/design` giúp quyết định cấu trúc code (tách storage/logic) có lý do rõ ràng, không phải đoán — quyết định đó sau này giúp viết test dễ hẳn.
- Task breakdown có DoD cụ thể (không phải "viết code cho xong") khiến từng bước code biết chính xác khi nào dừng.
- `/code-review` tìm ra 1 lỗi thật (JSON hỏng làm crash CLI, do `storage.load()` nằm ngoài khối `try/except`) — chứng minh bước review bắt buộc trước PR là xứng đáng, không nên bỏ qua kể cả với code nhỏ.

## Cái gì cần chỉnh

### 1. Đặt tên tag cần gắn slug của project con
Repo này là dạng nhiều project con dùng chung 1 lịch sử git (`projects/<slug>/`). Lần release đầu tiên đã tạo tag `v0.1.0` — nếu sau này có project con thứ hai cũng release `0.1.0`, tag sẽ đụng nhau. **Đề xuất sửa `/release`:** dùng format tag `<slug>-v<version>` (vd `todo-cli-v0.1.0`) thay vì `v<version>` trần, trừ khi repo chỉ có đúng 1 project con vĩnh viễn.

### 2. Version của project không có packaging cần chỗ khai báo rõ ràng
Project todo-cli không dùng `pyproject.toml`/`setup.py` (đúng theo ADR — giữ tối giản). Khi chạy `/release`, phải tự quyết định "file khai báo version" là gì (dùng `__version__` trong `__init__.py`). **Đề xuất sửa `templates/CLAUDE.md.template`:** thêm dòng gợi ý "Nếu project không có file packaging, khai báo version tại `<package>/__init__.py` (`__version__ = "x.y.z"`)" để lần sau không phải quyết định lại từ đầu.

### 3. Gộp review sau khi xong cả 4 task (thay vì review từng task) — chấp nhận được cho task nhỏ, nhưng cần nói rõ trong tài liệu
Task breakdown gốc đề xuất review sau mỗi task, nhưng thực tế đã gộp lại review 1 lần sau khi code xong cả 4 task để nhanh hơn. Với quy mô nhỏ (4 task, ít rủi ro) việc này ổn và không bỏ sót gì. Nhưng nếu số task nhiều hơn hoặc task có rủi ro cao, gộp review có thể làm bug tích tụ khó truy nguồn hơn. **Đề xuất:** không sửa quy trình bắt buộc, nhưng ghi rõ trong `docs/quy-trinh-phat-trien-phan-mem.md` giai đoạn 6: "Có thể gộp review sau nhiều task nhỏ rủi ro thấp; nên review riêng từng task nếu có task đánh dấu rủi ro Cao."

## Bài học chung (áp dụng lần sau)
- Kiểm tra `git config user.name`/`user.email` và `gh auth status` **trước khi bắt đầu** một project mới, không phải khi commit đầu tiên bị chặn — tránh gián đoạn giữa chừng.
- CRLF warning của git khi add file mới (do Windows) là bình thường, không phải lỗi — không cần xử lý.
